# 声音怎么走：这个工具的原理

想象一下你戴着耳机在打游戏，队友能听见你说话，靠的是游戏向手机要麦克风的声音。这个工具做的事，就是在你按下开关以后，把游戏要麦克风的那只手悄悄牵到音乐播放器上：队友听见的是你放的歌，不是你房间里的动静。这份文档把这个过程一步步讲清楚，不讲代码，只讲声音从哪来、中间经过了谁、最后到了哪里。读完你能知道它需要 root 权限、也必须先指定一个音乐软件。

## 一、手机里的声音是怎么分类的

手机内部有两股互不相干的声音通道：

- **播放通道（输出）**：音乐软件、游戏、系统提示音，都是往这条通道上送声音，最后到你的耳机或扬声器。
- **录音通道（输入）**：麦克风采集到的声音，App 通过这条通道读取，比如语音通话、录音机。

正常情况下两条通道没有任何交集：你在耳机里听到的歌，麦克风是听不见的。这个工具要做的，就是**在中间架一条自己的支路，把播放通道上某一路声音，接到录音通道的入口去**。

## 二、具体怎么接

手机上每个应用都像一个独立的房间，房间之间不能互相直接递东西。所以工具分三步来做这件事：

**第一步，在音乐软件那边截一份。**

音乐软件要把歌放出来，必须把声音交给手机系统。工具就在它交出去的那一刻，顺手复制一份。注意是"复制"——原来那份照常送给系统，所以你戴着耳机听歌一切如常，完全不受影响。

**第二步，把这份声音送到游戏那边。**

两个应用是两个互相隔离的房间，中间需要一条通道。工具在两边各开一端，用一条手机内部的私有管道连起来，把截到的声音实时传过去。

**第三步，在游戏那边，把它交给要麦克风的人。**

游戏读麦克风时，工具在这个环节把管道里的音乐塞给它。游戏拿到的东西，在格式上和它平时拿到的麦克风数据一模一样，分辨不出区别，直接编码发给队友。

于是：**你的耳机里有歌，队友的耳朵里也有歌，而真实麦克风的声音没有任何人去读。**

## 三、必须指定一个音乐软件

第一步里如果不去限定来源，而是把"整台手机正在播放的所有声音"都复制一份，那么连同游戏的枪声、脚步、系统提示音，全都会一起被送进麦克风。队友那边就会出现这样的效果：他听见你放的歌，同时也听见他自己刚才说的话、听见游戏里的枪声——这就是你最开始担心的**回音**。

所以界面里必须让你选中一个音乐软件，工具只截取它的声音。这不是可选项，是功能成立的前提。

## 四、作用范围：需要在框架里逐个勾选应用

工具的作用范围是**你在框架里勾选的那些应用**，不是整机全局。

- 只有被勾选的应用在开关打开时才会被接管；没勾的应用，麦克风照常是真实麦克风。
- 系统收发声音的那个程序**不在覆盖范围内**，工具无法从它入手。
- 想让某个应用生效，先在模块作用范围里勾选它；**新勾选的应用需要重启一次手机**才生效（和模块本身一样）。

这个范围限制同时带来了精确性：只截取你指定的那一个音乐软件，不会把游戏音效也送回去，因此不会产生回音。

## 五、开关关闭时会发生什么

关闭开关时，工具立刻不再往麦克风里塞音乐：

1. 游戏再读麦克风时，拿回的是它本来该拿到的真实声音；
2. 音乐那边也不再复制声音。

这一切不需要重启手机，**也不需要重启游戏**——工具在每次录音发生的那一刻都会重新看一眼开关，所以关掉就立刻生效。关掉以后，你说话队友就能正常听见。

## 六、出错了会怎样（两个兜底设计）

这类工具最怕"帮倒忙"：本想加分，结果把正常的语音功能弄坏了。所以刻意留了两层保护：

- **管道里暂时没有声音时**（比如你还没开始放歌），游戏读到的仍是它原本该读到的内容，而不是一片空白。这样即使这套机制一时没生效，你的游戏语音也还能正常用。
- **任何时候读不到设置**，工具都当作"开关是关的"来处理，让麦克风保持正常工作。宁可不出效果，也不要让你处于"以为关了、其实没关"的状态。

## 七、这件事需要 root

普通 App 出于隐私保护，不允许随便插手别的声音：既不能去截别人应用正在播放的声音，更不能去替换别人读到的麦克风数据。要越过这两条限制，就必须在系统层面动手，这需要 root 权限。相关的风险与权限用途单独写在 [security.md](security.md)。

## 八、专业名词对照

| 文档里出现的词 | 说白了就是 |
| --- | --- |
| 播放通道 / 输出 | 手机往外放声音的那条路 |
| 录音通道 / 输入 | App 从麦克风读声音的那条路 |
| 截取 / 捕获 | 把某个 App 正在播放的声音复制一份出来 |
| 管道 / 通道 | 两个应用之间那条私有的传声管道 |
| 替换 | 把游戏读到的麦克风数据换成别的内容 |
| 开关状态 | 你在界面上的那个总开关当前是开还是关 |

## 九、当前状态

截至本次更新，已经确认的事实（都是实机验证，不是推测）：

- 目标应用确实使用 Java 层的录音接口读麦克风（以王者荣耀为样本，它的 5 个代码包里都有录音读取调用），说明"在录音读取处替换数据"有真实的作用对象；
- 音乐软件确实使用 Java 层的播放接口送声音（以网易云音乐为样本，有播放写入调用），说明"截取音乐输出"也有真实的作用对象；
- 安装包能自动构建并成功装到手机上，而且**签名已经固定下来**——新版本可以直接覆盖安装，不必先卸载。

**代码目前做到哪一步**：上面三步都已经写好，采用在应用层面截取和替换的做法，不依赖系统里给录屏用的虚拟设备。

**还差的一步**：模块需要**重启一次手机**才会被框架正式加载。框架只在开机时扫描一次模块清单（新勾选的应用同理）。重启之后就能按 [testing.md](testing.md) 验证实际效果。

**一个实现上的限制**：用 `MediaRecorder` 录音的应用覆盖不到（它的声音数据不经过工具能插手的那一层）。王者荣耀这类游戏用的是另一种接口，在覆盖范围内。详见 [runbook.md](runbook.md)。

**实机验证记录（重启后）**：

- 模块确实被框架加载进目标应用，播放与录音两端的接口都挂上了（各 7 个重载）；
- 开关与选择确实能从界面传到运行在别的应用里的工具代码——这一条曾经不成立：界面用私有模式保存设置时，工具侧不会报错、只会一直读到默认值（开关看起来永远是关的），表现为"钩子都挂上了却从来不生效"。改用可被框架读取的模式后已修复；
- 音乐侧的通道套接字已实际建立，证明截取到的声音确实在往外送。
